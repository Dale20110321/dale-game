## 2. 你有两条主线，请按顺序判断

### 主线一：补完剩余 6 轮审查（第 5~10 轮）

spec.md 最前面的「📋 必读」一节列出了每轮的 14 个具体审查角度，**逐条照做，不要自行发挥替代**。

每轮的做法：
1. 用 **14 个并行 agent**，每个 agent 一个明确角度
2. 每个 agent 的 prompt 必须包含：
   - 项目路径 `C:\Users\1\Documents\GitHub\dale-game`
   - 「**只读审查，禁止修改任何文件**」
   - 具体的文件范围
   - 具体的检查项清单
   - 输出格式：`文件:行号 | 严重度 | 问题 | 复现 | 建议`，每条 ≤3 行，≤25 条
   - 「必须引用真实代码行，不要泛泛而谈；没发现就写无」
3. **每轮 agent 数必须是 14 个，不许断崖式减少**。若某个 agent 因 API 错误退出，立刻重试补位到 14 个。
4. 拿到结果后按第 3 节的流程回填。

### 主线二：按 tasks.md 实施修复

**审查没做完之前不要开始修代码。** 原因：第 5~10 轮会覆盖物理、存档、性能等与前三轮重叠但角度不同的维度，先修会漏掉后轮发现的连带问题（例如第 5 轮的"物理手感回归"会推翻第 3 轮对动力链的判断）。

审查全部完成后，从 `tasks.md` 的 Task 1 开始，严格按编号串行执行。

## 3. 硬性约定：审查发现的新问题必须进入 spec

**这是本规范最重要的一条维护机制。**

每完成一轮审查，**必须**做以下三件事：

### ① 落盘原始记录

写入 `.specs/fix-game-core-issues/audit/round-NN-<主题>.md`。

格式参照已有的 4 轮。每轮文件开头写明：轮次、主题、agent 数、完成数（失败的要写明哪个角度失败及原因）、以及一段「跨 agent 复现的高危问题」汇总表。

### ② 回填 spec.md

新发现的问题按性质归位：

| 发现性质 | 回填位置 |
|---|---|
| 级联/系统级缺陷 | `ADDED` 或 `MODIFIED Requirements`，并在 `What Changes` 对应阶段补条目 |
| 功能性 BUG | 归入最贴近的既有 Requirement 的 Scenario；不贴近就新建 Requirement |
| 死代码 / 技术债 | `REMOVED Requirements`，**必须**附 Reason + Migration |
| 只影响既有条目的细节 | 直接修订该条目的文字描述 |
| **已在 audit/ 但没进 spec.md** | 补齐 —— 已完成的 4 轮也可能有遗漏，接手时应对照审计文件核对 |

### ③ 追加后续任务到 tasks.md

在 `tasks.md` **末尾**按 `Task N.M` 递增追加（编号接续现有最大号，**不复用、不重排**已有编号）。每条任务注明来源轮次：

```markdown
- [ ] Task 12.3: 修复巡航层危险段不可见（第 6 轮发现）
- [ ] Task 12.4: 修复存档导入对畸形 JSON 的健壮性（第 7 轮发现）
```

### 不允许出现的情况

- ❌ 审查了但没写进 spec.md
- ❌ 审查了但没追加到 tasks.md
- ❌ 某轮因 agent 全挂就跳过该轮、不留记录
- ❌ 自行替换 spec.md 里已规划好的审查角度
- ❌ 为了"看起来完成"而降低每轮 agent 数

**即使某轮只发现轻微问题、或 14 个 agent 全部失败**，也要在 `audit/` 留一份记录写明「本轮无新发现」或「本轮因 API 错误未完成」，并在 tasks.md 追加一条「补做第 N 轮」的任务。

## 4. 审查时的技术提示

这个项目有几个特殊之处，写 agent prompt 时值得注意，能显著提升产出质量：

- **零依赖、零构建**，纯 ES module + Canvas 2D。不要建议引入框架或构建工具。
- **`src/config/` 是数据的唯一出处**。物理量换算只允许在 `config/constants.js` 里做 —— 这条规矩被写在 README 里，审查时要核查是否被绕过。
- **依赖是单向的**：`config ← physics ← game ← render/ui`。`render/` 不许 import `game/`。审查第 10 轮时要专门查反向 import。
- **代码注释密度极高，且大量注释记录了"曾经怎么错的"**。这些注释是审查线索的重要来源 —— 但也有不少注释已经与实现脱节（例如 `input.js:85` 写着"+/- 已移除"而 README 仍在宣传它）。两者都要报。
- **`groundY` 是全项目最热函数**（实测 3.1~253µs/次），涉及它的性能问题要重点看。
- **数值跨度极大**：金币跨 30 个数量级，速度跨 38 亿倍。审查时用脚本实测而不是目测，可以写临时脚本到系统临时目录（**不要写进仓库**）。

### agent 输出质量的两条经验

前 4 轮的实测结论表明，给 agent 这两条约束能显著提升有效产出：

1. **要求引用真实行号**（`文件:行号`）—— 否则会得到一堆无法定位的泛泛而谈。
2. **要求实测数值**（"实测""实测 27 台车 wMax 从 0.87 到 73.3 rad/s"）—— 第 3 轮最有价值的 5 个级联缺陷全部是 agent 写脚本实测出来的，不是读代码猜出来的。
